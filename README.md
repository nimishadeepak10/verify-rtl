# VerifyRTL

**LLM-assisted RTL verification: directed simulation and formal verification in one pipeline, with an emphasis on never reporting a stronger verdict than the tool actually earned.**

VerifyRTL takes a Verilog/SystemVerilog design and automates the parts of verification that usually eat the most engineering time: writing a testbench, picking a formal proof strategy, drafting properties, and triaging failures. It runs on real tools — [Icarus Verilog](https://bleyer.org/icarus/) for simulation, [SymbiYosys](https://github.com/YosysHQ/sby)/[Yosys](https://github.com/YosysHQ/yosys) for formal — and uses an LLM only where it adds real leverage: proposing properties from RTL structure, converting natural-language claims to SVA, and explaining a failing trace. Every verdict is grounded in an actual solver or simulator run; nothing is inferred or guessed.

## The gap this closes: verification plan → properties → verified

A verification plan states *what* a design must guarantee. Turning that into something a solver can actually check — and then running the check — is normally manual, disconnected work spanning specs, waveforms, and tool-specific syntax. That gap, not any single simulation or proof, is what VerifyRTL automates:

1. **What needs verification.** `vplan_builder.py` analyzes the RTL and produces a structured `VerificationPlan` (`vplan.py`): test categories (directed, corner, negative, random, exhaustive) and coverage goals (statement / branch / toggle / FSM / functional), each with an explicit rationale or N/A reason — not a blank template. For formal targets, `property_suggester.py` asks the same "what must this design guarantee" question directly against RTL structure and an optional spec, phrased as candidate assert/assume/cover claims instead of test categories.
2. **Convert to properties.** `property_to_sva.py` turns each candidate into a real SystemVerilog Assertion — and, critically, **declines** to convert anything genuinely multi-cycle rather than silently approximating it as same-cycle (see [Limitations](#limitations)). Only what's honestly checkable becomes a property.
3. **Verify with connected tools.** Every property runs through a real backend — [SymbiYosys](https://github.com/YosysHQ/sby) (BMC / unbounded PDR / k-induction, with the [engine/solver fallback chain](#formal-verification-engines-fallback-and-honesty) below) for formal, [Icarus Verilog](https://bleyer.org/icarus/) for simulation. The verdict is always the tool's own answer — `PROVEN`, `FALSIFIED`, `REACHED`, `UNREACHED`, or an honest `TIMEOUT`/`UNKNOWN` — never inferred.

**Worked example — `sync_fifo.v`** (a 4-entry, 8-bit synchronous FIFO). What a verification plan needs to check, and what actually happened when each claim was pushed through to a real solver:

| What needs verification | Property | Verified by | Result |
|---|---|---|---|
| Occupancy never exceeds capacity | `count <= 4` | SymbiYosys, PDR | **PROVEN** |
| `full` and `empty` are mutually exclusive | `!(full && empty)` | SymbiYosys, PDR | **PROVEN** |
| `full` flag matches occupancy exactly | `full == (count == 4)` | SymbiYosys, PDR | **PROVEN** |
| `empty` flag matches occupancy exactly | `empty == (count == 0)` | SymbiYosys, PDR | **PROVEN** |
| `full` is actually reachable, not just assumed | `cover(full)` | SymbiYosys, BMC | **REACHED** |
| No data loss: writes come back out in order | *(declined — see below)* | — | not approximated |
| A write while full doesn't silently corrupt state | *(declined — see below)* | — | not approximated |

The last two rows are as important as the first five: both are genuinely multi-cycle claims (they require relating a value written on one cycle to a value read several cycles later), and `property_to_sva.py` correctly refuses to convert them into a same-cycle approximation that would look verified but wouldn't actually mean what it claims. Every design in the [stress-testing section](#stress-testing-against-increasing-complexity) below has its own version of this table — see `scripts/test_*_suggestions.py` for the full proposed/expressible/proven breakdown per design, including the real bugs the process found along the way.

## Why this exists

Verification tooling has a well-known gap: the hardest part of the job isn't running one simulation or one proof, it's connecting specs, RTL, verification environments, coverage, and debugging into a coherent workflow across a project. VerifyRTL is an exploration of how much of that connective work an LLM-assisted pipeline can close — and, just as importantly, how honestly it can report the parts it *can't* close. A recurring theme throughout this project is refusing to let a tool limitation quietly become a false PASS.

## What it does

| Capability | Description |
|---|---|
| **Directed simulation** | Parses RTL, infers ports/clock/reset/FSM, generates a self-checking testbench (golden-model comparison where derivable, monitor-only with an explicit **UNVERIFIED** flag otherwise — never a green PASS the tool can't back up), runs it, and returns logs + an interactive waveform viewer. |
| **Formal verification** | Real SymbiYosys backend: BMC, unbounded PDR, and k-induction, with an automatic **engine/solver fallback chain** (see below) and honest `PROVEN` / `FALSIFIED` / `REACHED` / `UNREACHED` verdicts that are never conflated with `TIMEOUT` / `UNKNOWN` / `ERROR`. |
| **LLM-assisted property engine** | Proposes candidate assert/assume/cover properties from RTL structure and an optional spec, then converts each to SVA — and explicitly **declines** properties that are genuinely multi-cycle rather than silently approximating them as same-cycle claims. |
| **Coverage** | Post-pass code coverage (statement/branch/toggle/FSM) computed from VCD timelines, with an agentic closure loop that proposes new stimulus for uncovered targets. |
| **Spec traceability** | Maps written requirements to verification-plan test categories, surfacing gaps. |
| **Failure triage** | Chat-style Q&A over a failing waveform/trace to help localize root cause. |
| **CDC/RDC checking** | Static structural scan (not a proof) for unsynchronized clock-domain crossings and risky async-reset sources, covering the multi-clock gap the formal path above can't model. |

## Formal verification: engines, fallback, and honesty

The formal backend doesn't just run one solver and report what it says. `recommended_engine_chain()` (`src/rtl_verify/formal_props.py`) walks an ordered list of genuinely different proof strategies — confirmed against SymbiYosys's own source, not guessed from `--help` text:

- **Sequential assert/assume:** PDR → k-induction (yices) → k-induction (z3) → k-induction (bitwuzla). PDR and k-induction are different algorithms with different failure modes; an induction-step failure alone (base case still holding) correctly leaves the verdict unresolved rather than reporting a false counterexample, so the chain only advances past genuinely inconclusive results, never past a real `PASS`/`FAIL`. `cvc5` is deliberately left out of this specific chain — confirmed by direct testing to genuinely *hang* under this exact k-induction protocol (not just run slowly: a 20-second timeout budget left the process alive 45 minutes later), a real solver-specific incompatibility, not assumed or guessed at.
- **Cover (reachability):** the same bound, five different SMT solvers (yices, z3, boolector, cvc5, bitwuzla) — recovers from a solver-specific error without changing what's being searched for. `cvc5` runs here without issue — its incompatibility above is specific to the prove/k-induction query pattern, confirmed by testing it in this mode directly rather than blanket-excluding it everywhere.
- **Combinational:** a single BMC step is already exhaustive (SAT-complete), so there's no algorithm to fall back to.

Finding `cvc5`'s hang also surfaced a real bug in `backends/symbiyosys.py`'s timeout handling: on Windows, killing the top-level `sby` process does not kill the solver process it spawned as a grandchild (Python's `subprocess` module doesn't use Job Objects by default) — a hung solver could survive its own timeout indefinitely as an orphan. Fixed by killing the whole process tree (`taskkill /T` on Windows, the process group on POSIX) instead of just the immediate process — confirmed directly: the same hang now returns a clean `TIMEOUT` in the expected window, with no orphaned process left behind.

The wall-clock budget the caller sets is **split across the chain's rungs, never silently multiplied** — a documented `timeout_sec` stays a real budget. Every attempt is reported back, so an inconclusive final verdict is never opaque about what was actually tried.

`TIMEOUT` / `UNKNOWN` / `CANCELLED` are surfaced as their own honest verdicts, distinct from both a real proof and a real counterexample — confirmed against SymbiYosys's source that `UNKNOWN` is a real, reachable PDR outcome, not a hypothetical edge case.

**PROVEN isn't the last word, either.** A property can be technically PROVEN for a hollow reason — its own triggering condition never actually happens, so the "proof" says nothing about whatever it was meant to guarantee (`assert(a -> b)` where `a` is never true is trivially true and useless). Every PROVEN assert now gets an automatic **vacuity check** (`src/rtl_verify/vacuity.py`), not just the LLM-suggested properties that happen to carry a hand-written paired cover: it extracts the guard from this project's standard `!(guard) || (conclusion)` property shape and runs a real `cover(guard)` through the solver. The result — `NON_VACUOUS`, `VACUOUS`, `UNKNOWN`, or `NOT_APPLICABLE` (property isn't in that shape) — travels alongside every PROVEN verdict as a `confidence` field, so "PROVEN" is never shown without also saying how much that proof is actually worth.

**A single assert being vacuous is one failure mode; the whole *assumption set* being self-contradictory is a related, arguably worse one — it poisons every property in the same run at once, not just one.** Researched before writing any code, the same way this project's other formal-methodology features were: real FPV methodology guidance (EDN's own write-up on over-constraint in formal flows) states this plainly — "conflicting constraints... so constrained that there are no legal inputs, meaning that no assertions can fail, in effect because no checking is done." `src/rtl_verify/assumption_check.py` (`/api/formal`'s automatic `assumption_consistency` field, whenever any `assume`-kind properties are supplied) runs the natural sibling to the per-assert vacuity check: a real `cover(1)` under every supplied assumption applied together. If it's UNREACHED, the assumption set is genuinely self-contradictory — not a heuristic guess — and every PROVEN/UNREACHED verdict from that same run is suspect for exactly the reason above. When that happens, the specific culprit assumption(s) are isolated automatically via delta-debugging (iteratively drop one assumption, re-check reachability, keep the drop only if the contradiction persists without it) — the same idea Oski Technology's Anshul Jain describes in Verification Horizons for debugging vacuous proofs by minimizing constraints, rather than leaving an engineer to manually bisect a long assumption list by hand. Verified end-to-end with three real solver-based cases, not just unit tests: a single self-contradictory assumption (`wr_en && !wr_en`) correctly isolates to itself; two individually-fine assumptions that only conflict together (`wr_en` and `!wr_en`) correctly isolate to *both*, with a third, genuinely harmless assumption correctly excluded from the reported conflict set; and a real `assert` that would otherwise show a totally trustworthy-looking `PROVEN` under exactly this kind of contradictory assumption pair gets correctly flagged as hollow by `assumption_consistency`, not silently left looking fine (see `scripts/test_assumption_consistency.py`). Bounded to avoid runaway solver cost: isolation is skipped (reported honestly, not silently) above 8 supplied assumptions, since naive delta-debugging is worst-case quadratic in the number of extra solver calls it costs.

**"How many properties is enough, and are they actually any good?" now has a real, measured answer instead of a guess.** Researched from YosysHQ's own published methodology for its MCY (Mutation Cover with Yosys) tool: "test how good your test suite is at detecting errors in your design, by deliberately introducing... small mutations... and checking if they are caught." A property set that lets a real, syntactically-valid RTL change slip through completely undetected has a genuine, measurable gap — not a subjective feeling that "there should probably be more properties." `src/rtl_verify/mutate.py` generates single-operator mutations (relational/logical/bitwise/arithmetic — `==↔!=`, `&&↔||`, `&↔|`, `^↔~^`, `+↔-`, `<↔<=`, `>↔>=`) of a module's own body; `src/rtl_verify/mutation_adequacy.py` (the new `/api/formal/mutation_adequacy` endpoint) re-runs every already-PROVEN property against each mutant, reporting `CAUGHT` (a property failed — the set is sensitive to this class of bug), `NOT_CAUGHT` (every property still passed — a real gap, honestly caveated below), or `INCONCLUSIVE`.

This is deliberately a **simplified** subset of real MCY, not a reimplementation of it, and says so on every result: full MCY uses a separate netlist-level equivalence check to first filter out mutations that don't even change observable behavior; without that layer, a `NOT_CAUGHT` mutant here might be a genuine property-set gap, or it might be a behaviorally-equivalent change (dead code, a redundant recomputation) that no property could ever need to catch — this project has no way to tell the two apart automatically, and every report says so explicitly rather than implying more precision than it has. `<=`/`>=` are deliberately never mutation *sources* in either direction that would remove them: Verilog's `<=` is genuinely ambiguous between "less than or equal" (safe to mutate, inside an expression) and the nonblocking assignment operator (`lhs <= rhs;`, a statement) — confirmed a real, not hypothetical, risk by testing this exact case first: flipping `result <= a + b;`'s `<=` to `<` produces a bare invalid statement, not a behavioral mutant, and reliably telling the two apart needs real statement-level parsing this project doesn't have. `< -> <=` and `> -> >=` stay safe in the other direction, since the source token is never ambiguous.

Verified end-to-end with a real, deliberately incomplete property set, not just a hypothetical: a 4-opcode ALU with a property checking only the addition opcode correctly shows 1/4 real mutations caught and the other 3 — mutations in the subtraction/AND/OR branches this narrow property never inspects — correctly reported as honest, uncaught gaps; extending the property set to cover all four opcodes brings every one of those same 4 mutations to `CAUGHT`, a 100% kill rate (see `scripts/test_mutation_adequacy.py`). Every mutant is checked against only the single fastest engine in `recommended_engine_chain()`, not the full multi-engine fallback every other property check in this project uses — mutation testing already multiplies solver runs by the mutant count, and a full fallback chain per mutant would make this prohibitively expensive beyond a handful of mutants — and the mutant count itself is capped (`max_mutants`, default 20) for the same reason.

**The Dwyer/Avrunin/Corbett property-specification taxonomy was already partially adopted here — `property_suggester.py` already tags every proposed property with a pattern (Absence/Existence/Bounded Existence/Universality/Precedence/Response/Chain Precedence/Chain Response) — but its second, independent dimension, *scope*, was entirely missing.** Checked directly against the actual schema and prompt before writing anything, rather than assumed: `pattern` was a required field; `scope` didn't exist at all, and the `pattern` tag itself was write-only — captured from the LLM but never aggregated or reported anywhere downstream. Scope matters for hardware specifically, not just for taxonomic completeness: this project's own `$past()`-history guard (`generate_formal_wrapper()` wrapping every one-cycle-back claim in `!$initstate() && <reset not currently or previously asserted>`) was already, mechanically, always applying something functionally close to an *After-reset* scope — just never surfaced as a modeling decision a property author reasons about. `src/rtl_verify/spec_patterns.py` adds the five scopes (Global, Before, After, Between, After-Until, each with a hardware-flavored example) as first-class data, extends `property_suggester.py`'s schema with required `scope`/`scope_detail` fields, and — the genuinely new capability — `summarize_pattern_scope_coverage()` aggregates a property set's pattern and scope tags into real, visible gaps: a whole pattern category with zero representation (e.g. no `Precedence`-tagged property anywhere — has an ordering constraint really never been checked?) or every property being `Global`-scoped (has reset-recovery or a multi-cycle transaction's own invariants really never needed a narrower window?) is now something this project points at directly, the same way `mutation_adequacy.py` points at an untested code path, just from the specification-taxonomy angle rather than the RTL-coverage one. Wired into `/api/formal/suggest` as a new `pattern_coverage` field on every response. Verified end-to-end with a real LLM call, not just a schema check: `sync_fifo.v` proposed 18 real properties, all carrying a recognized pattern *and* scope tag, correctly split between mostly `Global` (16) and genuinely `After`-scoped (2, matching real reset-recovery claims) rather than every property being flattened to Global by default (see `scripts/test_spec_patterns.py`).

**Checking this project's own feature set against a published, named-source formal signoff methodology — SemiEngineering's "The Seven Steps of Formal Signoff" (the OneSpin/Siemens formal verification team) — turned up something worth noting before adding anything new: three of the seven published steps were already independently built here, converging with real industry practice rather than by design.** Step 1 (test plan/specification review) is `spec_traceability.py`; step 4 (over-constraint analysis) is `assumption_check.py`; step 7 (mutation testing) is `mutation_adequacy.py`. Two more — step 2 (designer review of properties) and step 5 (sequential-depth confidence assessment) — are inherently a human judgment call or already partially reflected in `recommended_formal_config()`'s depth heuristics, not something worth building a standalone feature to fake. Step 6 (solver-internal "formal core" extraction — which specific registers a given proof actually depended on) needs solver-internal machinery this project doesn't have access to, and isn't claimed here. That left step 3, genuinely missing and genuinely implementable: **cone-of-influence / verified-surface analysis** — "tracing backwards from assertions to identify which design elements are verified, revealing any registers, inputs, or outputs not being checked." `src/rtl_verify/signal_coverage.py` (`/api/formal`'s new `signal_coverage` field on every response) is a static textual scan — every property and assumption expression run in a given call, checked against the module's own port list — reporting which ports were never referenced by name at all. Deliberately honest about its own limits: a listed port being "covered" means some property mentions it, not that its full behavior is constrained (a real structural cone-of-influence trace would need a netlist/dependency graph this project's text-based analyzer doesn't build), and an uncovered *reset* port is flagged with an explicit caveat that this project's own `$past()`-history guard already handles reset structurally without it needing to appear in property text, unlike an uncovered *data* port. Verified end-to-end through the real API: a single narrow property on `sync_fifo.v` correctly shows 8% signal coverage (1 of 12 ports, including debug ports from `dut_probe.py`), and a property set deliberately written to touch every real port correctly shows 100% (see `scripts/test_signal_coverage.py`).

**Pushing this whole newer toolkit — auto black-box ranking, assumption consistency, signal coverage, mutation adequacy — together against a real design from a genuinely different domain (secworks/aes, a widely-used open-source AES-128/256 core) found one more real, honest gap and closed it.** `aes_core.v` instantiates its full encryption/decryption/key-schedule datapath even for a property purely about control-FSM correctness — `recommend_blackbox_candidates()` correctly flags all three real datapath blocks, exactly the shape this feature exists for. A real invariant (`ctrl_reg == IDLE` iff `ready`) proves cleanly via PDR with the whole datapath still in scope, `assumption_consistency` correctly reports `CONSISTENT` for a real protocol assumption, and `signal_coverage` honestly shows this narrow property leaves the entire encryption datapath (`block`, `result`, `key`) completely unverified — exactly the intended signal. But `mutation_adequacy` found nothing to mutate in `aes_core`'s own body at all: its control FSM is built entirely from `case` statements and named constants (`CTRL_IDLE`/`CTRL_INIT`/`CTRL_NEXT`), with zero relational/logical/bitwise/arithmetic operators anywhere in it — confirmed by grepping the real file, not assumed. `mutate.py`'s operator-swap families had nothing to touch despite the module having real, mutable control state. Fixed with a new **constant** mutation family: a sized Verilog literal (`2'h0`, `4'b0101`) incremented by one, wrapping within its own declared bit width — a standard, separate mutation-operator category in the wider literature, not RTL-specific. Re-verified the existing `tiny_alu` synthetic case with this addition: its 3 case labels now also mutate, correctly growing the mutant count from 4 to 7, with the deliberately narrow property now catching exactly 2 (the original arithmetic swap plus the new mutation that breaks the same op=00 branch's own case label) and the complete four-opcode property set catching all 7 — a 100% kill rate either way (see `scripts/test_real_design_aes_core.py` and the updated `scripts/test_mutation_adequacy.py`).

**Every check above assumes the property itself means what its author thinks it means — a real book of documented Intel false-positive post-mortems (Seligman, Schubert & Achutha Kiran Kumar's *Formal Verification*, Chapter 9, "Formal Verification's Greatest Bloopers") says that assumption is exactly where several real tapeout-reaching bugs came from.** Each case in that chapter is a property that compiled, ran, and PROVEN-passed while silently checking something other than what its author intended — a different failure mode than vacuity or over-constraint, both already covered above, and one no solver run can catch, since the property genuinely does pass; only reading the text catches it. `src/rtl_verify/sva_lint.py` (`/api/formal`'s new `sva_lint` field on every response, always computed, no solver involved) implements four of these as real static rules, each mapped to its source case: **`missing_semicolon`** — an assert/assume/cover with no terminating `;` and no `else` clause, where SVA silently treats whatever comes next as this assertion's own pass-action instead of running it independently every cycle (the book's real "missing semicolon" Intel bug, found by a validation engineer at a late project stage); **`short_circuit_assertion_function`** — a function containing an assert/assume/cover, called as the non-first operand of `||` or `&&`, where SystemVerilog's short-circuit evaluation can silently skip the call (and its assertion) entirely; **`moving_sampled_index`** — a `$past`/`$stable`/`$rose`/`$fell`/`$changed` call indexing an array with a non-constant, non-genvar signal, generalized from the book's concurrent-assertion example to this project's actual `$past()`-based immediate-assertion style (see `docs/formal_property_reference.md`), deliberately excluding genvar-indexed accesses (`$past(state[gp])`) since a generate loop's own index is a compile-time constant per instance, not the runtime-varying hazard this rule targets; and **`generate_label_collision`** — a statically labeled assert/assume/cover inside a genvar-driven `generate for` loop, which isn't from the book at all but is a confirmed limitation of this project's *own* yosys build (see the MESI repo's "Notable findings" section), now caught automatically instead of rediscovered by hand. Two of the book's cases — assertions clocked on both edges (`@(clk)` vs `@(posedge clk)`), and weak-vs-strong `s_eventually` liveness confusion — were deliberately *not* implemented, since both are concurrent-SVA constructs (`assert property (@(...) ...)`) that this project's own yosys build rejects outright with a parse error (confirmed, not assumed); a lint rule for syntax this project's tools can't even compile would never fire and would only manufacture false confidence that this class of bug had been checked for. Verified against real RTL both ways: all four rules fire correctly against small synthetic examples built to match each book case exactly, and — the false-positive check that actually matters — running the linter against the real, committed MESI repo's three RTL files (which use exactly the genvar-indexed `$past()` pattern the moving-index rule has to not flag, and exactly the unlabeled-generate-loop convention the label-collision rule has to not contradict) returns zero findings (see `scripts/test_sva_lint.py`).

**Black-boxing is all-or-nothing per module; two finer-grained abstraction techniques now sit below it.** Adapted from the abstraction toolkit in Seligman et al.'s *Formal Verification* (Ch. 10), Siemens' Verification Horizons complexity-reduction series, and the FVM complexity-reduction guide. **Cut points** (`src/rtl_verify/cutpoint.py`, `/api/formal`'s `cut_signals` and `auto_cutpoint` options) free ONE internal signal instead of a whole submodule: its driving logic is dropped and the solver may choose any value for it every cycle. Implemented with yosys's own `cutpoint` pass rather than a source rewrite, because a text-based analyzer cannot reliably tell a register's reads from its writes. Two things were learned empirically while building it, not assumed: yosys's `cutpoint` on an un-flattened module only cuts the net as seen from OUTSIDE it (the module's own internal consumers still saw the original driver), so the backend flattens first; and the cut alone did not speed anything up until `opt_clean -purge` was added, because yosys keeps any cell still driving a public-named wire even with no loads. Names are validated against the module's declarations (a typo is an error, never a silent no-op), the clock/reset and bare inputs are refused, and `auto_cutpoint` only fires on a genuinely inconclusive verdict, after auto-black-boxing had its chance, trying the top three wide-counter/accumulator or wide-multiply/divide candidates one at a time (the FSM state register is never proposed). Soundness is directional and stated on every result: PROVEN under a cut still holds for the real design; FALSIFIED may be an artifact, and the cross-check is skipped because it would compare different designs. Measured on a real design (an arbiter gated by a wide accumulator fed by the MAC pipeline), plain vs. cut, same property: 24 stages 20.4s vs 2.4s; 100 stages 65.9s vs 2.8s; 500 stages 89.9s vs 21.0s; 600 stages a genuine four-engine TIMEOUT (132s) vs PROVEN in 28.9s. The honest limit visible in those numbers: a cut cannot save yosys's elaboration of logic that is merely dead, so the cut run still grows with pipeline size (28.9s at 600 stages) where black-boxing a module stays flat. **Assertion decomposition** (`src/rtl_verify/assertion_decompose.py`, `decompose` option) splits a compound assert into parts whose conjunction is exactly the original, using the two identities `!(a || b) || c == (!(a) || c) && (!(b) || c)` and `!(g) || (x && y) == (!(g) || x) && (!(g) || y)`. Both are exact, so the original is PROVEN iff every part is and FALSIFIED iff any part is; the response names which part failed, and the test checks equivalence by brute-force truth table over every input assignment rather than by eye. It only splits at the top level (an OR nested in parentheses, a conclusion that is itself an OR, or a single-char `|` are left whole). Smoke-tested on the arbiter: a compound grant property split in two, one half PROVEN and the other FALSIFIED, pinpointing the failing sub-claim (see `scripts/test_cutpoint_and_decompose.py`; pass `--solver` for the real-engine runs).

**Two more abstractions from the same sources, deliberately opposite in how much they can be trusted: one is exact, one is not.** **ROM-to-case** (`src/rtl_verify/rom_abstract.py`, `/api/formal`'s `rom_to_case` option) rewrites a read-only memory as a combinational `case` lookup, removing DEPTH x WIDTH state bits while keeping every line of control logic. Siemens' memory-abstraction write-up singles this variant out as the safe one, and it is: the rewrite has exact semantics (the lookup takes a full 32-bit address with a `default: x` arm, so out-of-range reads behave like the original array, with no truncation aliasing), so both PROVEN and FALSIFIED stay valid and nothing needs a caveat. Because it must never guess, it refuses anything it cannot be sure about and says why: any write outside an `initial` block (that is a RAM), `$readmemh`/`$readmemb` (contents live in a file it cannot see), non-literal initial indices, and reads that are further bit-selected. An ineligible memory is left byte-for-byte untouched. One real bug surfaced while testing it against the solver: the generated lookup function originally used the non-ANSI `input [31:0] a;` form, which this project's text-based analyzer scans for as a module port, so the DUT instantiation failed with "no port named 'a'"; it now uses an ANSI-style argument list. Verified by running the same property on the original and rewritten design: a true property is PROVEN in both and a deliberately wrong one FALSIFIED in both, with the 128 state bits of a 16x8 ROM reported as removed. **Parameter reduction** (`src/rtl_verify/param_reduce.py`, `param_overrides` and `auto_param_reduction`) re-runs the proof on a smaller configuration of the same design (a 600-stage pipeline becomes 4 stages), rewriting literal defaults in the target module's parameter list and literal values in its instantiations' `#(.NAME(n))` override lists; `localparam`s and expression-valued parameters are never touched. **This one is NOT sound for the full configuration, and every result says so.** The test makes the point concretely rather than by assertion: a saturating counter with `LIMIT = 16` and the property `c != 10` is FALSIFIED at its real size and PROVEN at `LIMIT = 4`, so a reduced-configuration PROVEN can simply be wrong for the real design. For that reason the auto path is the last resort (after auto-black-boxing and auto cut points), only proposes parameters whose names count structure (depth/stages/entries and similar, never data widths, since shrinking a width is only sound when data never steers control and that is not checked), reports every verdict as a bounded configuration, and skips the cross-check. A name that matches no literal parameter is an error, not a silent no-op. On the real stuck design (a 600-stage MAC pipeline gating an arbiter, a genuine four-engine TIMEOUT at full size), `param_overrides=STAGES=4` and `auto_param_reduction` both reach PROVEN, the latter picking `STAGES` 600 -> 4 by itself (see `scripts/test_param_reduce_and_rom.py`; pass `--solver` for the real-engine runs).

**Counter abstraction** (`src/rtl_verify/counter_abstract.py`, `/api/formal`'s `counter_abstraction` and `auto_counter_abstraction` options), adapted from the counter-abstraction technique in Seligman et al.'s *Formal Verification* (Ch. 10), Siemens' Verification Horizons complexity series (Part 4) and the FVM complexity guide, attacks sequential depth rather than state size: a 32-bit timeout counter needs up to 2^32 cycles to expire, so no bounded engine can reach, or refute, anything behind it. Each `cnt <= cnt + 1` is rewritten to `cnt <= __cabs_inc_cnt`, where the new value is `jump ? <one step before the next critical value> : cnt + 1` and `jump` is a free (`anyseq`) bit. With `jump = 0` that is exactly the original increment, so every real behavior is still possible; with `jump = 1` the counter skips to just before a value the design compares it against (one before, not on it, so the real +1 into the threshold still happens). The abstract design's behaviors are a superset of the real design's, which is why a PROVEN verdict stays valid for the real design while a FALSIFIED verdict or REACHED cover may rely on a skip the real counter could only reach after the full count; both directions are stated on every result, and the cross-check is skipped. Critical values come from static comparisons of the counter against literals or numeric parameters (all six relational operators) and from bit tests like `cnt[31]`; missing one costs precision, never soundness, because the +1 path is always kept. A statement-level `cnt <= 0;` is correctly not mistaken for a comparison (checked by parenthesis depth), only exact `x <= x + 1` increments are rewritten (clears, loads and holds are untouched), the helper declarations are placed after the counter's own declaration (a wire using `cnt` before `reg cnt` would not elaborate), and a name with no literal-width declaration or no increment is an error rather than a silent no-op. As an escalation, `auto_counter_abstraction` runs after auto-black-boxing and before auto cut points (it is sound for proofs and more precise than freeing the signal) and abstracts the widest counters that have critical values, flagging any counter that is also an output port, since a property on its exact value can see a skipped count. Verified with real engines on a timeout controller whose bug sits 1,000,000 cycles deep (`timed_out == 0` asserted, and it is false): the plain run never decides (PDR TIMEOUT and three k-induction UNKNOWNs), while both the manual option and the automatic escalation find the FALSIFIED trace. The soundness check that matters was run on the same design with a limit of 20, where the plain proof is cheap: a true property is PROVEN both plain and abstracted, a false one FALSIFIED both ways; and a true property is still PROVEN on the full 1,000,000-cycle design (see `scripts/test_counter_abstraction.py`; pass `--solver` for the real-engine runs).

**Every abstraction above is either sound or loudly labeled; case-splitting is the one standard complexity technique that is neither, and it has a documented way of failing silently.** Splitting a proof into several runs, each restricted by a case assumption (one opcode range, one mode), is unsafe in a way black-boxing and cut points are not: each case ADDS an assumption, and nothing checks that the cases add up to the whole space. Seligman et al.'s *Formal Verification* (Ch. 9) documents two real post-mortems of exactly this: an arithmetic block with a 6-bit exponent was split into 0..31 and 33..64 and the forgotten value 32, a power of two and the one risky case, hid a real bug until much later; and a PCIe block was "verified" in x8 mode only while the change touched logic shared with x4 and x16. Every individual run was green in both. `src/rtl_verify/case_split.py` (`/api/formal/case_split`) turns the gap from a review comment into a solver result: given the cases, the shared (global) assumptions, and the asserts, it (1) proves `case_1 || case_2 || ...` under the global assumptions, so a legal input in no case comes back as a concrete uncovered example read from the counterexample (`{'e': 32}`); (2) runs `cover(case_i)` per case, so a case the global assumptions already rule out is flagged empty (its proofs would pass for no reason); (3) checks, for each input signal a case mentions, whether `x == $past(x)` holds under the global assumptions, because the coverage check is per cycle and a case signal that varies over time lets behaviors that mix cases across time belong to no run even when every single cycle is covered (reported as `SPLIT_PROVEN_PER_CYCLE_ONLY` rather than a full pass, with the varying signals named); and (4) proves each assert once per case. It deliberately cannot judge whether the cases are the RIGHT ones for the design's risk, only that nothing is missing and nothing is empty. Verified on the book's own scenarios with real engines: the exponent split reproduces the trap exactly (both runs PROVEN, completeness a GAP with the uncovered example `e = 32`, overall `SPLIT_INCOMPLETE`), and adding the forgotten `e == 32` case completes the split and, for the first time, exposes the real bug as FALSIFIED in that one case; a mode split (x4/x8/x16) over a 2-bit mode is a GAP at `mode = 3` until a legitimate `mode != 3` assumption is added; a case contradicting the global assumptions is flagged empty; and on a sequential design a free split signal gives the per-cycle-only verdict while an assumption holding it constant gives a full `SPLIT_PROVEN`. Building the test also turned up a real width bug in my own test design (`4'd16` truncates to 0 in a 4-bit output) that the tool reported correctly as a FALSIFIED in the x16 case (see `scripts/test_case_split.py`).

**Data independence** (`src/rtl_verify/data_independence.py`, `/api/formal`'s `data_signals`, `data_width_reduction` and `auto_data_width_reduction`) closes the gap the earlier parameter-reduction feature had to leave open. Both Seligman et al.'s *Formal Verification* (Ch. 10) and the FVM complexity guide say a datapath width can be shrunk when correctness depends on transport and control and not on the payload, and both attach the same condition: "only when data values don't affect control behavior." `param_reduce.py` refused to touch widths because nothing checked that condition. This module checks it with a taint (information-flow) analysis over the module's text: the named data signals are seeds, taint propagates through every assignment (including through registers and memories), and the control sinks are then examined: the condition of an `if`/`while`/`for`, a `case` selector, the select of a `?:`, and any array or bit-select index. A tainted signal reaching one is `DEPENDENT`, reported with the signal, the kind of sink and the line; anything the analysis cannot see through (tainted data connected to a submodule port, or passed to a user function) is `UNKNOWN`, never `INDEPENDENT`. The analysis also records whether the design merely MOVES data or COMPUTES on it, because the two justify different things. If data cannot influence control, the control-state sequence is identical at every width, so a property that mentions no data signal gets an EXACT result at a reduced width. A property that does mention data is only covered when the design is transport-only (data is copied, selected or stored, never combined by an arithmetic, logic or comparison operator) and the property uses data by equality; a multiplier bug that only shows in the upper bits would simply vanish at 4 bits, so those properties are refused. A width is reduced only through a parameter that sizes data signals and nothing else (no clean signal's range, no use outside declaration ranges and replications). Verified both ways with real engines: a FIFO whose data never reaches its pointers is `INDEPENDENT` and its `WIDTH` 32 to 4 gives the same PROVEN control verdict; a design with `if (wr_en && wr_data == 8'hFF)` is `DEPENDENT`, the reduction is refused, and the refusal is shown to be right, since forcing `WIDTH=4` anyway flips the real FALSIFIED to a wrong PROVEN (the 8-bit constant can no longer match). Taint is shown to propagate through a register (`flag <= d[0]; if (flag)` is caught at the `if`), a ternary select and an index; a submodule connection gives `UNKNOWN`; an adder is control-independent but not transport-only, so a data property on it is refused while a control property on the same adder is allowed at the reduced width. The auto escalation was exercised on a genuine timeout (a 900-stage MAC pipeline gating an arbiter) and correctly declined to reduce because independence came back `UNKNOWN`; I did not find a design where a data-independent transport design is hard enough to time out, so the positive auto path is covered by the manual-path tests and the shared escalation machinery, not by its own stuck-proof demo (see `scripts/test_data_independence.py`; pass `--solver` for the real-engine runs). Two real bugs found while building it: the analyzer treated a parameterized array such as `reg [W-1:0] mem [0:DEPTH-1]` as a scalar (its range evaluator only knew the descending `W-1:0` form), so the debug-probe instrumentation emitted `assign __dbg_mem = mem;` on a whole array and the design failed to elaborate; it now evaluates ascending parameterized ranges and skips, rather than mis-probes, an array it cannot size. And every new `Form(...)` option on `/api/formal` silently broke each script that calls the handler directly (an omitted option arrives as a `Form` object, not its default), so those scripts now import a small `scripts/_formal_call.py` wrapper that fills in the real defaults.

**Helper invariants are mined, then proven, never trusted.** A proof by induction stalls when the property is true but not inductive: the solver finds an unreachable state that satisfies it now and breaks it a step later. The usual remedy is a helper invariant that rules that state out, and finding one by hand is the slow part. With `mine_invariants` (or `auto_invariants`, tried before any abstraction), the design runs under constrained-random stimulus in Icarus Verilog, and facts that held on every sample are proposed: a register stayed within a small set of values, a vector stayed one-hot, a counter never exceeded a bound, two flags were never high together, one flag always implied another. Every candidate then goes into one k-induction run together; whatever the solver can violate is dropped (false from reset, or not inductive given the rest) and the survivors are re-checked until a run passes, which is the Houdini fixed point. Only the survivors become assumptions for the real property, so a PROVEN or FALSIFIED verdict keeps its meaning: nothing was abstracted, only unreachable states were removed. The test suite shows the stuck case closing (`q != 4'b0110` on a one-hot ring is UNKNOWN under k-induction alone and PASS with the mined invariants), a false candidate and a true-but-non-inductive one both being dropped, and a ring with a wrong reset value still FALSIFIED with mining on. Mining can miss the invariant a proof needs, and `invariant_candidates` accepts your own expressions, which go through the same disposal. 

**Each assumption has to earn its place.** Every `assume` removes behaviors from a proof, so every one is a place a bug can hide; the MESI assumption that two caches never read in the same cycle looked harmless and ruled out a legitimate scenario. With `check_assumptions`, each PROVEN assert is re-proved with the assumptions removed one at a time from the current set: a still-PROVEN result means that assumption was not needed given the rest and is dropped, and a counterexample means it was needed, and the trace is returned so you can see exactly which behavior it excludes. What remains is a subset-minimal proof core, and assumptions that no checked property needed are listed so they can be deleted. The result is order-dependent when two assumptions exclude the same behavior (each is removable, not both), and the output says so. It also never judges whether a needed assumption is reasonable, only what it forbids. It costs one proof per assumption per property, so it is opt-in and capped. 

**Assertions are searched per signal, and scored by the solver.** Adapted from SANGAM (Gupta, Mali, Karfa, IEEE ICLAD 2025), `/api/formal/assertion_search` runs a Monte Carlo Tree Self-Refine loop for each signal: a deliberately short root answer, then rollouts that select a node by UCT, ask the model to refine it from feedback, evaluate the result, and back-propagate with Q' = (Q + max child Q) / 2. Where the paper scores nodes with a critic LLM (which its authors found overly optimistic and had to damp) and checks only syntax, the reward here comes from real runs: each assertion is classified as a syntax or unknown-signal error, FALSIFIED, vacuous, redundant with the others, or proven and independent, and the model is shown the counterexample values rather than a log. Redundancy, which the paper lists as an unsolved limit, is checked by a solver with the design taken out, since every proven assertion is trivially implied by the design itself. The signal-mapping step is a set intersection of what the specification and the RTL both name, so a mapping cannot be hallucinated. FALSIFIED assertions are returned with their counterexamples for a person to judge (a wrong claim or a real bug), never counted as successes. Not adopted: the waveform analyzer (no image input here). Not claimed: the paper's assertion counts or coverage numbers, which this has not been benchmarked against. The test suite pins the search arithmetic, the classification, and the combination with a scripted refiner, and one live run against the model keeps only proven assertions. 

**Forward progress is checked as a bound, and failures are named.** Adapted from LUBIS EDA's write-up on deadlock, livelock and starvation in SoCs, `/api/formal/progress` turns "this request must eventually be answered" into the safety property the open-source engines can prove for all time: a monitor counts how long a request has waited and asserts it never exceeds N. Fairness is an explicit, reviewable assumption (an environment condition that must hold at least once in every M cycles, encoded as a counter), and a PROVEN result reports which fairness assumptions it actually needed, so a plausible-sounding one that the proof did not use can be dropped. A failing bound comes back with the counterexample read structurally: the resource was granted to others (starvation), the design froze (deadlock-like), or it kept changing state without completing (livelock-like). That label is a heuristic over one trace and says so; it is not a deadlock proof. `find_bound` searches for the smallest provable N and reports "no bound up to the cap" rather than claiming unbounded starvation is proven. In the tests, a fixed-priority arbiter is starved until the higher-priority requesters are assumed to pause every third cycle, and the round-robin arbiter in the examples is starved by unbounded backpressure but served within 12 cycles once backpressure drops every third cycle.

**Nor is a single engine's opinion.** The chain above already contains genuinely independent implementations (PDR/`abc`; k-induction via `yices`, `z3`, or `bitwuzla`; `boolector`/`cvc5`/`bitwuzla` for covers) — but until now they were used purely as a fallback, stopping at the very first PASS/FAIL. `src/rtl_verify/cross_check.py` (`/api/formal`'s `cross_check` option, on by default) re-runs every definitive verdict against one more, genuinely different engine and compares. Agreement is real evidence the result isn't a tool-specific artifact — worth having, since this project found two real bugs *in yosys's own SystemVerilog frontend* in a single session (a silently-dropped `bind` statement, a hierarchical dot-reference that resolved to an unconstrained value instead of erroring) that a second, independent tool would very plausibly not share. A disagreement is surfaced as its own field, `agrees: false`, with both engines' verdicts named — never silently resolved by trusting either side.

**Verdicts don't just expire silently when RTL changes, either.** `src/rtl_verify/regression.py` records every property's last verdict per module (`regressions/<module>.json`, hashed against the exact RTL it was checked against). The next time `/api/formal` runs against that module, if the RTL's hash has changed, every previously-recorded property is automatically re-run — not just whatever this specific call happens to submit — and the new verdicts are diffed against the old ones. A property that used to be PROVEN and now isn't is reported as a real `regression` (old verdict, new verdict, both named); the reverse (something that used to fail now passes) is reported as `fixed`; nothing changing means a clean, fast no-op. There's no daemon watching files — the trigger is the next real verification call against that module, which is enough to make "did I just break something I already proved" something the tool answers on its own rather than something a user has to remember to re-check by hand.

**Proof cost doesn't have to scale with the size of blocks a property doesn't semantically depend on, either.** Every example above is teaching-sized; a real chip has many genuinely-used blocks, only a few of which matter to any one property. `src/rtl_verify/blackbox.py` (`/api/formal`'s `blackbox_modules` option) replaces a named submodule's entire body with a stub of the same name/ports/parameters whose outputs are left genuinely undriven, so the solver treats them as free instead of reasoning about that submodule's real internal logic at all. This only matters when the "irrelevant" block's output actually feeds into the property's logic — two genuinely *disconnected* blocks already get discarded by a solver's own automatic cone-of-influence reduction for free, confirmed by testing that exact case first and finding no speed difference either way. `scripts/test_blackbox_reduction.py` demonstrates the real case: a small round-robin arbiter's grant logic gated by one bit derived from a 200-stage 32×32 multiply-accumulate pipeline's actual accumulator value — real numbers from running it, not simulated: 24 stages ~3.0s → 200 stages ~12.9s *without* black-boxing (proof cost genuinely grows with the pipeline's size), flat at ~2.1s *with* it, matching the standalone arbiter's own proof time regardless of how large the black-boxed block behind it is — the same PROVEN verdict either way, since the property never depended on what the pipeline actually computes.

**Choosing which modules to black-box no longer has to be manual, either.** Before writing any code, this was researched against real industry practice rather than guessed at: Siemens' own Questa formal verification team publishes the exact trigger real teams use — black-box only *after* a proof is confirmed stuck (never pre-emptively), reaching first for large memory/register arrays in the active logic cone, since state-heavy structures are the most consistently cited cause of formal engines failing to converge; the arithmetic-circuit-verification literature separately and consistently documents wide multiply/divide operators as a long-standing hard case for bit-level SAT/BDD reasoning, independent of whether a given property needs the exact arithmetic result. `recommend_blackbox_candidates()` (`src/rtl_verify/blackbox.py`) encodes this as a real, ranked, tested policy over a module's own directly-instantiated submodules: a large memory/register-array declaration ranks highest (a parameterized, not-statically-sizable array is still flagged, conservatively, but ranked below a confirmed-large numeric one), wide arithmetic next, and body size as a last resort. `/api/formal`'s new `auto_blackbox` option wires this into the existing engine chain: only when a property comes back genuinely inconclusive (TIMEOUT/UNKNOWN/CANCELLED — never overriding a real PROVEN/FALSIFIED) does it retry with the top-ranked candidate black-boxed, one at a time, stopping at the first definitive verdict. Every attempt is recorded, and a verdict reached this way carries its own explicit `auto_blackbox` field naming exactly what was abstracted, with a caveat that's directional depending on the outcome — a resulting PROVEN is real but weaker than a full-whitebox one (it assumes the abstracted module's real behavior doesn't matter to this property), while a resulting FALSIFIED may be a black-box artifact (the abstracted module's now-free outputs triggering behavior impossible in the real design) that needs the trace checked against that module's real logic before being trusted as a genuine bug.

Verified end-to-end with a real solver run, not just unit-tested in isolation: reusing this project's own black-boxing stress design at a much deeper pipeline (800 stages, versus the committed example's 200) so the plain proof genuinely exceeds a 40-second budget — a real `TIMEOUT`, not a contrived one — `auto_blackbox` correctly identifies `wide_mac_pipeline` as the top candidate and rescues the property to a real `PROVEN` in seconds, with the same design left honestly `TIMEOUT` when `auto_blackbox` is off (see `scripts/test_auto_blackbox_rescue.py`). Building this end-to-end test surfaced one more real bug, in the formal backend itself, not this new feature: SymbiYosys can crash internally with its own Python traceback (`AttributeError: 'NoneType' object has no attribute 'hierarchy'`) if its wall-clock timeout fires *while yosys synthesis is still running*, before writing its own status file — this project's backend wrapper was defaulting that case to a bare `ERROR`, which would have silently blocked `auto_blackbox` from ever triggering on exactly the large, slow-to-synthesize designs it exists to help with (an `ERROR` triggers an LLM syntax-fix retry, not black-box escalation). Fixed in `backends/symbiyosys.py` by recognizing sby's own "Reached TIMEOUT" log line even when the status file is missing, and classifying that case as the honest `TIMEOUT` it actually is.

**One-cycle-back claims are now supported, generalized rather than hand-built per design.** Every earlier one-cycle temporal check in this project — the RVFI-based RISC-V properties, the MESI coherence model's transition rules, the internal-signal fill-tag check — was written by hand, each remembering its own reset/first-cycle guard. `generate_formal_wrapper()` now does this structurally: any property using `$past()` is automatically wrapped in `!$initstate() && <reset not currently or previously asserted>`, so a "previous cycle" / "next cycle" claim just needs its actual logical content — no caller (human, LLM, or script) has to get the guard right by hand. This was a real policy reversal, not a default: an earlier version of this codebase banned `$past()` outright, citing an unreliable verdict "likely" tied to async-reset modeling — re-investigated here with a dedicated isolated probe (an unbounded PDR proof, since a bounded check could simply not run long enough to hit the race) before lifting the ban, rather than assuming the old caution no longer applied. Concurrent SVA (`assert property (@(posedge clk) ...)`) remains unsupported by this yosys build — confirmed again against a newer 2026-09-24 oss-cad-suite release via its bundled `slang` frontend: the syntax now parses, but the actual sequence-implication operators (`|->`, `|=>`, `##`) needed to express a claim this way are still "unsupported SVA feature" in yosys's own SVA lowering, so `$past()` inside a plain `assert(...)` remains the only working substitute, not a stopgap waiting to be replaced.

**Pushing the formal pipeline itself against a genuinely complex real design for the first time — `YosysHQ/picorv32.v`, not just the CDC scanner — surfaced a real, cross-cutting bug in `analyze_rtl()` itself.** `picorv32.v` declares its RVFI ports (and several internal trace registers) inside `` `ifdef RISCV_FORMAL ``, a macro this project's formal backend never defines (SymbiYosys's own `read -formal` convention implicitly defines only `FORMAL`). `analyze_rtl()` had never resolved `` `ifdef ``/`` `ifndef `` at all — it included every port that textually appeared in the source, regardless of whether a real, default synthesis build would actually compile it — so `generate_formal_wrapper()` built a DUT instantiation connecting a port plain synthesis doesn't have, a hard yosys error on the very first real property attempted against this design, not a proof-complexity problem. Fixed by resolving every `` `ifdef ``/`` `ifndef `` in `analyze_rtl()` itself against `{"FORMAL"}` as the only macro assumed defined, reusing `strip_ifdef_blocks()` (originally built for `cdc_check.py`'s own structural scan). That reuse exposed a second, more subtle bug in `strip_ifdef_blocks()` itself: its original `exclude_macros` parameter silently treated *every other* macro as defined by default (keeping its `` `ifdef `` branch, dropping its `` `else ``) — backwards from what either caller actually needs. Rewritten to take a `defined_macros` set with the safe default (undefined) applying to everything else, matching what a real build with no extra `-D` flags actually compiles. `cdc_check.py`'s own call site changed accordingly (from `{"FORMAL"}` treated as "exclude" to an empty "nothing is defined" set — the same real-hardware-only view as before, now on a more correct default). This retroactively corrected `picorv32`/`picorv32_wb`'s previously-reported register counts (162/22, down from 185/38) by excluding RVFI-only registers that don't exist in a real build — zero crossings either way, a precision fix, not a new finding. Verified end-to-end with a real solver run against picorv32.v's actual RTL, not just the wrapper-generation step in isolation (see `scripts/test_ifdef_port_resolution.py`).

**Multi-clock designs are unmodeled by the formal path above, so a separate static scan now checks what the solver can't.** `src/rtl_verify/cdc_check.py` (`/api/cdc`) is deliberately *not* a formal proof — it's the same category of first-pass structural check real CDC lint tools (SpyGlass CDC, Conformal CDC) run before any deeper netlist-level analysis. It groups a design's `always` blocks by clock signal, finds registers driven in one clock domain that get referenced in another, and traces how many plain-capture register stages (`stage2 <= stage1; stage1 <= source;`) sit between the crossing signal and its first non-capture use: zero stages is `UNSYNCHRONIZED`, one is `WEAK`, two or more is `LIKELY_OK` (with a standing caveat on multi-bit buses, since depth alone doesn't make a plain register crossing safe without gray-coding or a handshake). A separate reset-domain check flags any async-reset trigger that isn't a primary input or a registered signal — e.g. one derived from combinational logic — as `RISKY`, since a glitch on that combinational path can assert/deassert the reset at an arbitrary, unclocked instant. Validated on `alexforencich/verilog-axis`'s real `axis_async_fifo.v`: 12 real crossings found (11 `LIKELY_OK`, 1 `WEAK` — investigated against the source and confirmed to be an honest finding, not a heuristic bug: that signal really is captured only once before being used directly in pointer arithmetic, made safe only by a separately-synchronized handshake flag this structural scan correctly can't vouch for), 0 `UNSYNCHRONIZED`, both reset signals `OK`; a single-clock sanity check (`rv32i_core.v`) confirms zero false-positive crossings.

Pushing this scanner against more varied real RTL — `ZipCPU/wb2axip`'s `afifo.v`, `skidbuffer.v`, and `alexforencich/verilog-axis`'s `axis_fifo.v` — surfaced three more real gaps, all found and fixed the same way as everything else in this section: confirmed against the actual source, not assumed:

- The `always`-block scanner originally skipped single-statement blocks with no `begin`/`end` (silently dropping a whole clock domain built from one-line synchronizer stages), and the depth tracer originally only searched the one `always` block where a crossing was first referenced instead of the full destination domain — undercounted a real 2-stage synchronizer spanning two separate blocks in `axis_async_fifo.v`.
- A ZipCPU-style `` `ifdef FORMAL ``-guarded proof-only clock abstraction (`(* gclk *) reg gbl_clk;` — a scaffolding register that doesn't exist in synthesized hardware at all) was being scanned as if it were a genuine third clock domain in `afifo.v`, producing two fabricated `UNSYNCHRONIZED` findings. Fixed with a new `strip_ifdef_blocks()` (`analyzer.py`) that blanks out the branch guarded by known verification-only macros before any structural scan runs.
- The real gray-code pointer synchronizer in `afifo.v` was invisible to this checker twice over: it's written as a concatenation-target shift register (`{ wr_rgray, rgray_cross } <= { rgray_cross, rgray };`, a common way to pack several synchronizer flops into one line), which the single-identifier capture-chain tracer didn't recognize at all; and that line lives in the `else` arm of an `if (!rst) ... else ...` with no enclosing `begin`/`end`, which the block extractor was truncating at the `if` arm's first semicolon, discarding the `else` arm — the actual capture — entirely. Both fixed (a dedicated concatenation-shift matcher; a proper recursive statement consumer that follows `if`/`else`/`begin...end` instead of stopping at the first `;`). Re-run against `afifo.v` after both fixes: the real 2-stage `rgray`/`wgray` gray-pointer synchronizers are now correctly found and reported `LIKELY_OK`, where they previously vanished into a phantom domain and a truncated capture chain. `axis_fifo.v` and `skidbuffer.v` (both genuinely single-clock) correctly report zero crossings.

Scaling up further to `YosysHQ/picorv32.v` — a real, silicon-proven RISC-V core, 3000+ lines, and the largest design run through this checker so far — surfaced a fourth real bug, more structural than the first three: the CDC scanner was reading the *entire raw file*, not just the target module's own body. `picorv32.v` defines 8 modules in one file (the core itself, register file, multiply/divide co-processors, AXI and Wishbone wrapper variants); scanning the whole file for `always` blocks meant a completely unrelated module's clock leaked into the target's report — `picorv32_wb`'s own `wb_clk_i`-clocked logic was being attributed to the actual `picorv32` core, fabricating a second clock domain and several crossings that don't exist in that module at all. Fixed by scoping the scan to the target module's own body first (reusing `analyzer.py`'s own `_extract_module_body()`, the same boundary logic `analyze_rtl()` already relies on) before any `always`-block scanning happens. Re-run after the fix: `picorv32` (the actual core) correctly reports a single `clk` domain with zero crossings; `picorv32_wb`, analyzed as its own separate target module in the same file, correctly reports its own `wb_clk_i` domain in isolation — each module's report now depends only on that module's own text, not on what else happens to share its file.

Pushed to genuine SoC scale next: `alexforencich/verilog-ethernet`'s `eth_mac_1g_fifo` — a real 1G Ethernet MAC with TX/RX FIFOs. The top-level file alone is a thin ~330-line wrapper around submodules defined in *separate* files (`eth_mac_1g`, an async-FIFO adapter, the async FIFO itself, GMII rx/tx framing, an LFSR for CRC) — exactly the documented multi-file limitation below — so all 6 real dependency files were concatenated in, per that same documented workaround, producing a real, hierarchical, 3500+ line, 7-module combined design bigger than `picorv32.v`, from an entirely different codebase. Unlike the earlier rounds, this one found **no new bugs** — a genuinely clean result that confirms the fixes above generalize rather than being overfit to `afifo.v`/`picorv32.v`'s specific shapes. It did surface a new complexity milestone: `eth_mac_1g_fifo` itself is a real **3-clock-domain** design (`tx_clk`, `rx_clk`, `logic_clk` — more domains than anything validated before), with 2 real crossings, both correctly `LIKELY_OK` at depth 3; `eth_mac_1g` (one level down) has its own separate, correctly-isolated 2-domain link-fault-control handshake; and `axis_async_fifo`'s previously-validated 12-crossing result came back byte-for-byte identical despite now being buried 4 modules deep inside a much larger combined file — the strongest confirmation yet that the module-scoping fix holds regardless of how large or how deeply nested the surrounding file gets.

Pushed further still to the 10G variant, `eth_mac_phy_10g_fifo` — the same MAC/FIFO shape, but now with a full 10G BASE-R PHY layer (scrambling/descrambling, block synchronization, bit-error-rate monitoring, link watchdog) instead of a simple GMII interface. Its real dependency chain is both wider and one hierarchy level deeper than the 1G case (`fifo → phy_10g → rx_if/tx_if → frame_sync`/`ber_mon`/`watchdog`, vs. the 1G design's 3 levels), needing 11 additional real dependency files fetched and concatenated in alongside the 3 already used for the 1G case — a real, hierarchical, 5000+ line, 14-module combined design. Again, **no new bugs**: `eth_mac_phy_10g_fifo` reports the identical 3-clock-domain/2-crossing pattern as its 1G sibling (both correctly `LIKELY_OK`), `axis_async_fifo` now sitting 4 modules deep still reports its exact 12-crossing result unchanged, and every pure-wrapper module in the chain (instantiation only, no `always` blocks of its own) correctly reports zero domains rather than inheriting a neighbor's. All 14 modules resolved in about 1.1 seconds combined.

Then tried the largest, most complete assembly yet: **PicoSoC on iCEBreaker**, the actual example SoC shipped in `YosysHQ/picorv32` — a real, board-deployed RISC-V system combining the core (already validated above), a QSPI flash memory controller (`spimemio` + its own `spimemio_xfer` submodule), a UART (`simpleuart`), a vendor SPRAM wrapper, and the board-level top module (`icebreaker.v`, reset generation + I/O). Concatenated per the same documented workaround into a 4269-line, 16-module file spanning two different subdirectories of the same repository. This board design has no PLL and no dual-clock memory anywhere — it's genuinely single-clock by construction — so every module reporting zero crossings here is the *correct, honest* answer, not a checker limitation; the value of this round was confirming that at 16 modules, `picorv32` and `picorv32_wb` (embedded in yet another, even larger combined file) still report their exact standalone register counts (177 and 9) unchanged, and all 16 modules resolve in well under a second combined. Third consecutive round with **zero new bugs**.

The streak of clean rounds ended on `alexforencich/verilog-pcie`'s `dma_psdpram_async.v` — a real asynchronous dual-port RAM, structurally different from every design tried so far: instead of a control signal or pointer crossing domains through flip-flops, the actual *data* crosses through a shared memory array (`mem[wr_addr] <= wr_data;` on `clk_wr`, `rd_data <= mem[rd_addr];` on `clk_rd`), written with a nested-bracket LHS (`mem[wr_addr[hi:lo]][7:0] <= ...`, a real byte-enable pattern). The scanner's LHS-detection regex only understood a single, non-nested bracket group, so it never recognized `mem` as a register driven in `clk_wr`'s domain at all — the crossing wasn't misclassified, it was **completely invisible**, a more serious gap than any of the earlier rounds (zero crossings reported where a real one exists, rather than a wrong verdict on one that was at least seen). Fixed with `_lhs_identifier_before()`, a bracket-depth-aware backward matcher (handles arbitrarily nested index groups) replacing the old single-bracket regex everywhere an LHS is identified, used consistently by both the register-cataloguing step and the capture-depth tracer. The crossing is now correctly surfaced as `UNSYNCHRONIZED` — with a dedicated note distinguishing it from a flip-flop crossing: reading directly out of an array indexed by the other domain is a *memory-based* crossing, where the right question is "is the underlying RAM a genuine dual-port primitive," not "is there a missing synchronizer register," and the note says so explicitly rather than implying the generic fix applies. This fix also retroactively found the exact same real pattern already present in `axis_async_fifo.v`'s own FIFO storage array (`mem[rd_ptr] <= ...`), invisible in every earlier round's result — re-run after the fix: 13 crossings now (up from 12), with the FIFO's storage array correctly flagged `UNSYNCHRONIZED` and clearly annotated. This is, in fact, the textbook-correct way to build an async FIFO (the data path crosses via a true dual-port memory; safety comes from the already-validated gray-code pointer synchronization, not from synchronizing the memory read itself) — exactly the kind of thing this tool is honest about not being able to certify on its own, now correctly flagged for review instead of silently missed.

The next round, against `alexforencich/verilog-ethernet`'s VCU118 25G example (`fpga_core.v`, the board-level integration top, plus its own `sync_signal.v` — a parameterized N-stage synchronizer meant to be *instantiated* at every crossing rather than hand-inlined), surfaced the most significant scope boundary found in this whole series — not a miscount this time, but a genuine "doesn't know the crossing exists" gap. `sync_signal.v` itself has only one clock port: the actual domain crossing only exists at the *call site*, where its `in` port is wired to a signal from a different clock's logic. Since this scanner only reads a module's own `always` blocks, a crossing signal that's fed into an *instantiated* synchronizer submodule — rather than captured by a hand-written flip-flop in the same module — never appears inside any `always` block body this scanner looks at, so it's invisible. Confirmed directly with a dedicated synthetic test: a two-clock design where domain A's signal is properly synchronized through an instantiated 2-flop submodule before domain B consumes it reports **zero crossings** — not `LIKELY_OK`, not `UNSYNCHRONIZED`, nothing. Since real, professionally-organized RTL overwhelmingly synchronizes exactly this way (a reusable sync primitive instantiated wherever needed, rather than duplicated flip-flop chains), this is a real, non-hypothetical blind spot, not an edge case — documented prominently in [Limitations](#limitations) and locked in by a dedicated regression test (`HIERARCHICAL_SYNC` in `scripts/test_cdc_check.py`) so a "0 crossings" result on a design using this pattern is never mistaken for "verified safe." Fixing this properly needs genuine hierarchical elaboration (resolving each instantiation's own clock and recursing into its definition) — deliberately not attempted as a rushed heuristic in the same pass that found it, matching this project's standing preference for an honest documented gap over an approximate, under-tested new capability.

The sharpest confirmation of this same limitation came from `fpga.v` — the *actual, deployed* top-level integration file for the VCU118 25G board example, not a synthetic case. It instantiates real Xilinx UltraScale+ primitives (`MMCME3_BASE` for the internal PLL, `IBUFDS_GTE4` for MGT reference clock buffers) and drives per-QSFP-port MAC clocks, an SGMII PHY clock, and the PLL-derived core clock — structurally the most multi-clock-complex design in this entire series. Yet it has exactly **one** `always` block of its own (a small reset generator on the PLL clock); every real cross-clock relationship is expressed purely through instantiation port connections to the MAC IP cores (already validated separately) and `sync_signal`/`sync_reset` instances. Running the checker against it reports one domain, zero crossings — not because `fpga.v` is single-clock (it very much isn't), but because none of its real complexity lives in text this scanner reads. This is the sharpest possible illustration of why a clean CDC result on an integration-level top file must never be read as "verified safe": top-level files are almost always instantiation-heavy with minimal inline logic, which is exactly where this scanner's blind spot is worst.

**That gap is now closed, one instantiation level deep.** `_hierarchical_crossings()` (`cdc_check.py`) resolves a crossing synchronized by *instantiating* a reusable submodule, not just one hand-inlined with flip-flops. For every directly-instantiated module defined in the same submitted RTL text, it resolves which caller-side signal drives the instance's own clock port, attributes the instance's output-port-connected signals to that clock domain (so further downstream use is caught by the ordinary same-module algorithm for free), and — for every input port fed by a signal from one of the caller's *other* domains — reports a crossing with the capture depth traced *inside the instantiated submodule's own body*, reusing the exact same `_sync_depth_for_crossing()` that intra-module crossings use. Re-running the motivating synthetic case: the crossing through an instantiated 2-flop submodule is now correctly found and reported `LIKELY_OK` at depth 2 — and, symmetrically, a *broken* instantiated synchronizer (one that mixes its input into an expression instead of a plain capture) is correctly reported `UNSYNCHRONIZED`, not given a free pass just for being wrapped in a submodule.

Building this surfaced one more real bug worth calling out: `YosysHQ/picorv32`'s own `picorv32_wb` wrapper does `assign clk = wb_clk_i;` before instantiating the CPU core with `.clk(clk)` — a completely ordinary way to rename a clock signal, but naive hierarchical tracing treated `clk` and `wb_clk_i` as two *different* domains for the exact same physical clock net, fabricating two fake `UNSYNCHRONIZED` crossings between a signal and itself. Fixed with `_resolve_clock_alias()`, which walks a chain of simple `assign a = b;` continuous-assignment aliases back to whichever name is already a known domain, before treating an instance's clock connection as a new one. Also handles concatenated port connections (`.in({uart_rxd, uart_cts})`, a real pattern found in `fpga.v`'s own board-level wiring) by splitting them into their constituent bare identifiers rather than skipping the whole connection.

Re-run against every previously-validated real design after this feature landed: `fpga.v` now correctly discovers `fpga_core`'s own clock domain (walking straight through its `clk_390mhz_int` continuous-assignment alias to the true root clock name) with zero crossings — an honest result, since `fpga_core`'s inputs really are primary board I/O, not registers from `fpga.v`'s own domain. `picorv32` and `picorv32_wb`'s own register counts grew (185 and 38, up from 177 and 9) as their own instantiated sub-blocks' outputs were correctly folded in, with zero new false crossings in either case. Every other previously-validated design (`axis_async_fifo.v`, the 1G/10G Ethernet MAC assemblies, PicoSoC) came back byte-for-byte unchanged, since their direct instantiations are either purely combinational or themselves already-unsupported multi-clock modules — both gracefully skipped, not guessed at.

Scope, deliberately: only **one level** of instantiation is traced per call (the target module's own direct instantiations, not its instantiations' instantiations); a callee not defined in the submitted text, one that's itself multi-clock with no single identifiable clock port, or a port connection that's a genuine expression (not a bare identifier or a concatenation of them) is skipped gracefully rather than guessed at. Full recursive elaboration to arbitrary hierarchy depth remains future work — analyze each intermediate module directly (as this project's own test suite already does for every real design) to see crossings nested deeper than one level.

Rather than validating this pipeline only against toy designs, it's been deliberately run against a sequence of harder RTL — each one chosen to test a *different* axis of difficulty, with results reported honestly, including the failures:

Every one of these designs was independently verified against real simulation (Icarus) before any formal claim was trusted against it — several of the "findings" above turned out, on inspection, to be testbench bugs rather than RTL bugs, and are reported as such rather than glossed over.

Adding internal-signal visibility touches shared pipeline code (`analyzer.py`, the formal wrapper path), so after it shipped, every prior sign-off was re-run end to end rather than assumed safe: RV32I's 63/63 RVFI properties and MESI's 25/25 safety/correctness properties + 8/8 coverage goals all re-confirmed with zero regressions. Re-confirmed again after adding `cvc5`/`bitwuzla` to the engine chain and fixing the process-tree timeout-kill bug in `backends/symbiyosys.py` — both touch shared formal-backend code — with the same zero-regression result.

## Formal deep-dive: MESI cache coherence protocol

A separate, hand-built formal project (`examples/mesi_multi_cache.v` + `examples/mesi_cache_core.v`, `MESI_Formal/`) — SymbiYosys and hand-written SVA directly, not routed through VerifyRTL's LLM-assisted pipeline above, since proving cross-cache coherence invariants needs a genuinely multi-instance formal model (N=3 caches sharing one line over a snooping bus), not a single-DUT wrapper. Full test plan through sign-off: [`docs/verification_plan_mesi.md`](docs/verification_plan_mesi.md).

**Proved by k-induction (unbounded, not a bounded sample):** mutual exclusion of the Modified state across all 3 caches; the general single-writer invariant (E/M implies sole ownership — no stale-Shared cache can coexist with a Modified one); correct read-miss classification (Exclusive vs. Shared depending on whether another cache already holds the line); unconditional invalidation on a remote write; and the "silent upgrade" (E→M with no bus transaction) optimization. 25/25 safety and functional-correctness properties PROVEN; 8/8 coverage goals reached, including a full ownership-transfer transaction confirmed by hand from the raw VCD trace, not just the solver's summary label.

Two real yosys-frontend limitations were found and worked around while building this: bare concurrent SVA (`assert property (@(posedge clk) ...)`) isn't accepted by this project's yosys build at all (confirmed with an isolated probe, independent of this design) — substituted with `$past()`-based immediate assertions; and a static assert/cover label repeated across `generate for` iterations collides on cell naming — per-instance checks are left unlabeled, with SymbiYosys still identifying the failing cache via its hierarchical instance path. Both are documented in the plan, not silently patched around.

## Architecture

```
RTL upload → analyzer.py (ports, clock/reset, FSM, is_sequential)
          ├─ simulation path:
          │    combinational_model.py / rtl_interpreter.py (golden model where derivable)
          │    → generators/ (verilog | sv | uvm) → backends/ (pluggable simulators)
          │    → waveform.py (VCD → JSON) → coverage.py
          └─ formal path:
               property_suggester.py + property_to_sva.py (LLM, optional)
               → formal_props.py (engine/solver chain selection)
               → backends/symbiyosys.py (SymbiYosys: BMC / PDR / k-induction)
```

Both paths share the same analyzer and the same pluggable backend registry (`backends/registry.py`) — new simulators or solvers plug in as small modules, not pipeline changes.

## Limitations

- Property conversion reaches exactly **one clock cycle back** (`$past()`, structurally guarded against the first cycle and reset transitions — see below) — genuinely multi-cycle (more than one cycle back/forward) or liveness claims are still honestly declined, not approximated. This is a deliberate boundary, not an oversight, and its edge is exactly what the complexity-validation designs above are chosen to probe.
- Self-checking simulation depends on a derivable golden model; otherwise runs are monitor-only and flagged `UNVERIFIED`.
- FSM path coverage is directed, not formal.
- Internal-signal visibility (`dut_probe.py`) is capped at 24 registers per design by default (override by naming specific signals) and, like the rest of this pipeline, is same-cycle only — an internal array's debug select index is a free input, so a property comparing it *across* two cycles must explicitly pin the index stable itself (see `property_suggester.py`'s prompt) or it will silently compare two different array entries.
- **Genuinely multi-clock designs (CDC) aren't formally modeled** — the formal path above assumes a single clock domain throughout. `analyze_rtl()` correctly detects a design with more than one distinct clock-driven `always` block (e.g. an async FIFO's `wr_clk`/`rd_clk`) and reports it as such (`RtlModule.has_multiple_clocks`); `generate_formal_wrapper()` refuses to build a check for it rather than silently producing a wrong one — confirmed this was a real, not hypothetical, risk: an earlier version of this pipeline built a combinational-style check for exactly this case (since it only looked at whether *a* clock name matched, not whether the design was safely single-clock), while separately picking a genuinely-clocked proof mode for the same design. Only a design with a single non-standard-named clock (e.g. `clk_i`, `sys_clk`) is now additionally supported (structural fallback: the port used as the first trigger in `always @(posedge X ...)`), not multi-clock ones. For genuine multi-clock designs, `cdc_check.py` (`/api/cdc`) covers the gap with a static structural CDC/RDC scan instead — see [above](#formal-verification-engines-fallback-and-honesty) — but that scan is explicitly a lint-style heuristic, not a proof: it can flag a missing synchronizer but can't certify a protocol-level handshake is correct.
- Only tests one input file's worth of multi-file real-world designs at a time — a real design that instantiates a submodule defined in a separate file needs that file concatenated in first; the pipeline doesn't resolve cross-file dependencies on its own (confirmed by testing a real design with exactly this shape).
- **The CDC/RDC scanner (`cdc_check.py`) traces instantiated synchronizer submodules only ONE level deep.** A crossing synchronized by *instantiating* a reusable synchronizer primitive (the idiomatic, professional way real engineers write this — see e.g. `alexforencich/verilog-ethernet`'s own `sync_signal.v`) is resolved if that submodule is directly instantiated by the analyzed module and defined in the same submitted RTL text — confirmed against both a synthetic case and the real, deployed VCU118 board top (`fpga.v`), which now correctly discovers `fpga_core`'s own clock domain through this path. What's still out of scope: a crossing synchronized *two or more* instantiation levels away from the analyzed module (analyze the intermediate module directly instead — this project's own test suite does exactly that for every real design); a callee not defined in the submitted text (the multi-file limitation noted above applies here too); a callee that's itself an unsupported multi-clock module with no single identifiable clock port; and a port connection that's a genuine expression rather than a bare identifier or a concatenation of them (`.in({a, b})` is resolved, `.in(a ? b : c)` is not). A clock-renaming continuous assignment at the instantiation site (`assign clk = wb_clk_i;`, a real, ordinary pattern — confirmed on `picorv32_wb`) is correctly resolved back to the underlying domain, not mistaken for a second clock. Treat a "0 crossings" result on a design with deeper (2+ level) instantiation chains or unresolved connection shapes as **"not fully analyzed,"** not "verified safe" — this scanner is honest about which of these apply on a per-instance basis (see each crossing's own `note`), not silently uniform.
